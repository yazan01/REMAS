# REMAS — منصة تقييم النضج المؤسسي للمطوّرين العقاريين

منصة متعددة المستأجرين لتقييم النضج المؤسسي، مبنية على [خطة التنفيذ](https://claude.ai/code/artifact/4804259c-3a17-4b14-9574-bf05d19b5be6) المشتقّة من `REMAS BRD-V1.0`.

- **الباك إند:** Python · FastAPI · SQLAlchemy · SQLite محلياً (PostgreSQL بتغيير سطر واحد)
- **الفرونت إند:** Next.js 15 · TypeScript · CSS design tokens
- **اللغة:** عربي وإنجليزي بزر تبديل فوري في أعلى كل شاشة، مع انعكاس اتجاه كامل (RTL/LTR)

## التشغيل

### ١. الباك إند

```bash
cd backend
python -m venv .venv
./.venv/Scripts/python.exe -m pip install -r requirements.txt   # Windows
# source .venv/bin/activate && pip install -r requirements.txt  # macOS / Linux

./.venv/Scripts/python.exe -m app.db.seed --reset               # زرع المحتوى والحسابات
./.venv/Scripts/python.exe -m uvicorn app.main:app --port 8010 --reload
```

- الواجهة البرمجية: <http://127.0.0.1:8010/api/v1>
- التوثيق التفاعلي: <http://127.0.0.1:8010/docs>

> المنفذ 8010 وليس 8000، لأن 8000 مشغول على جهازك بتطبيق آخر.

### ٢. الفرونت إند

```bash
cd frontend
npm install
npm run dev
```

التطبيق على <http://localhost:3000>.

> **البناء الإنتاجي يكتب في `.next-build` لا في `.next`.** المجلدان منفصلان عمداً: البناء والـ dev server كانا يتشاركان `.next`، فالبناء يعيد كتابة ملفات الـ chunks التي ما زال الـ dev server يخدمها، فتموت الصفحة بـ `Cannot find module './960.js'`. بهذا الفصل يمكن تشغيل `npm run build` في أي وقت — في طرفية موازية أو في CI — دون إسقاط الخادم العامل.

## الذكاء الاصطناعي والـ OCR

خمس مراحل في `backend/app/services/ai/`، والقاعدة الحاكمة: **الذكاء الاصطناعي يقترح ويشرح، ولا يحتسب ولا يعتمد** (FR-26).

| المرحلة | ما تفعله |
| --- | --- |
| `extract` | استخراج النص من PDF/DOCX/XLSX/PPTX مع أرقام الصفحات، وOCR للممسوح ضوئياً |
| `relevance` | مقارنة الدليل بالسؤال والمستند المتوقع |
| `explain` | مرجع لكل ملاحظة: المستند، الصفحة، المقطع |
| `analyse` | نقاط قوة وفجوات وسرد لكل محور وللمنشأة |
| `recommend` | مبادرات من مكتبة iValue وخارطة طريق مُرحَّلة |

**مزوّدان للتحليل:** بلا مفتاح API يعمل مزوّد **حتمي** بلا أي اتصال شبكي. مع `ANTHROPIC_API_KEY` صياغة أغنى عبر Claude. الدرجات تأتي من محرك الاحتساب وحده في الحالتين.

### الـ OCR للمستندات الممسوحة (AI-01 · AI-07)

Tesseract 5.4 مثبّت مع نماذج `ara` و`eng` من `tessdata_best`، ويُطلب `ara+eng` **صراحةً لا بالكشف التلقائي** — وهو مصدر معظم فقدان الدقة في العربية. Azure Document Intelligence جاهز كبديل سحابي بالتهيئة.

**AI-07 يطلب «بيان حدود النموذج وضوابط الجودة». هذا القياس:**

```
المصدر            n     CER      WER    ثقة المحرك   الحكم
print-300dpi      5    1.6%    24.7%      90.0%     صالح
scan-200dpi       5   63.7%    72.0%      81.8%     غير صالح
photo-150dpi      5  100.0%   100.0%      95.0%     غير صالح
fax-100dpi        5  100.0%   100.0%      95.0%     غير صالح
```

#### الحدّ المكتشَف — أهم ما في القياس

**ثقة Tesseract لا تدلّ على دقته في العربية.** أبلغ عن ثقة ٩٥٪ في صفحات قرأها حساءَ رموز. الاعتماد على ثقة المحرك وحدها كان سيمرّر **١٥ من ٢٠ صفحة بمعدل خطأ ٥٥٪**.

#### الضابط الذي عالج ذلك

**بوابة ثانية مستقلة**: تقييم «معقولية النص» يقيس **بنية الكلمات لا نوع الحروف**. الـ OCR الفاشل في العربية يُخرج حروفاً عربية فعلاً — لكنها تصل كشظايا من حرف أو حرفين بدل كلمات.

```
جملة عربية حقيقية    0.942
جملة إنجليزية        1.000
حساء رموز            0.431   ← يُرفض
شظايا                0.172   ← يُرفض
```

**النتيجة بعد البوابتين:**

```
ما يمرّ من البوابتين       متوسط الخطأ    3.8%   (7 صفحات)
ما يُرفَض ويُحال للمراجعة    متوسط الخطأ  100.0%   (13 صفحة)
```

النظام لا يقبل قراءة رديئة صامتاً أبداً. وبلا مزوّد مهيّأ يوسم المستند بـ `ocr_required` **ولا يدّعي قراءته** — استخراج فارغ صامت كان سيجعل مرحلة تغطية الأدلة تصف دليلاً سليماً بأنه ناقص.

**معالجة مسبقة:** تدرّج رمادي · مدّ تباين · مرشّح وسيط عند اكتشاف ضوضاء · إعادة قياس إلى النطاق الذي دُرِّب عليه المحرك. القياس أظهر أن الحجم الأكبر **يضرّ لا ينفع** — التجزئة تبدأ بكسر الكلمات.

**الحد المعلَن:** القياس على **حزمة اصطناعية** تدهورها أقسى من المسح المكتبي المعتاد، فالأرقام المنخفضة ليست حكماً على مستنداتك. ضع ١٠–١٥ مستنداً عربياً حقيقياً مع نص مرجعي `.txt` وشغّل `--corpus` — عندها يصبح الرقم قرار اعتماد. التبديل إلى Azure **تهيئة لا كود**.

```bash
python -m scripts.ocrbench                    # الحزمة الاصطناعية
python -m scripts.ocrbench --corpus ./docs    # مستندات iValue الحقيقية
```

### توافق المتصفحات — مُختبَر آلياً

```
chromium  27/27  0 أخطاء   → Chrome و Microsoft Edge
firefox   27/27  0 أخطاء   → Firefox
webkit    27/27  0 أخطاء   → Safari
```

ثلاثة محركات تغطي المتصفحات الأربعة التي يذكرها الـ BRD: **Edge مبني على Chromium** منذ ٢٠٢٠، و**WebKit هو محرك Safari** نفسه. اختبار المحرك هو ما يكشف التعارضات الحقيقية: خصائص CSS المنطقية، `structuredClone`، سلوك `Intl`، وترتيب النص ثنائي الاتجاه.

كل محرك يُفحص على: نجاح كل صفحة · **صفر خطأ console أو شبكة** · ختم `dir`/`lang` · تبديل اللغة يقلب الاتجاه فعلاً · ثبات الاختيار بين الصفحات · تسجيل دخول حقيقي · وصول بيانات الـ API المُصادَق عليها · **غياب أي تمرير أفقي** عند 1400px و390px · تحوّل رموز الـ palette · رسم الوضع الليلي.

```bash
python -m scripts.browsertest --shots ./shots
```

**ما لا يغطيه اختبار المحرك:** واجهة المتصفح نفسها، الإضافات، وخصوصيات نسخة الشحن. تمريرة يدوية أخيرة على Safari وEdge الحقيقيين تبقى في قائمة القبول — لكنها تأكيد، لا اكتشاف.

**ملاحظة جانبية:** الاختبار كشف خللاً حقيقياً في إمكانية الوصول — `aria-label` لزر اللغة كان يصف اللغة الحالية بينما فعل الزر هو التبديل، فقارئ الشاشة يسمع عكس ما يحدث. أُصلح.

## الأمن

- **التشفير عند التخزين:** كل ملف دليل يُشفَّر بـ AES-256-GCM. المفتاح **مشتق لكل مستأجر** عبر HKDF، فنسخة خام من القرص أو من نسخة احتياطية لا تكشف بيانات مستأجر آخر. الاختبار `test_cross_tenant_key_cannot_decrypt` يثبت الرفض.
- **إدارة الأسرار:** `JWT_SECRET` و`EVIDENCE_MASTER_KEY` تُقرأ من متغيّر أو من ملف (`*_FILE`) بالاصطلاح الذي تستخدمه أسرار Docker وKubernetes. خارج بيئة التطوير **يرفض النظام الإقلاع** على القيمة الافتراضية أو على مفتاح أقصر من 32 بايت.
- **إدارة الثغرات:** `pip-audit` جزء من الأدوات. رُقّيت `cryptography` و`pillow` و`PyJWT` و`starlette` و`python-multipart` و`pypdf` لإغلاق ثغرات كانت في مسار معالجة ملفات العملاء مباشرة.

```bash
python -m app.core.keygen        # توليد مفتاح جاهز لمخزن الأسرار
python -m pip_audit              # فحص الثغرات
```

## التشغيل والنسخ الاحتياطي

```bash
python -m scripts.backup create              # أرشيف مشفّر
python -m scripts.backup verify <file>       # استعادة فعلية + فحص سلامة + قياس RTO
python -m scripts.loadtest --users 15        # قياس المتطلبات غير الوظيفية
python -m scripts.browsertest                # توافق المتصفحات على ٣ محركات
python -m scripts.ocrbench                   # قياس دقة الـ OCR العربي
python -m pip_audit                          # فحص ثغرات الاعتماديات
```

**RPO** = الفاصل بين تشغيلات `create` (يُنصح بساعة). **RTO** = يطبعه `verify` (قيس: 0.21 ثانية على بيانات الاختبار). الاستعادة تتحقق من سلامة قاعدة البيانات وتؤكد بقاء عزل المستأجرين.

نقاط المراقبة: `/health` (حيوية) · `/health/ready` (جاهزية القاعدة والتخزين والمزوّدين) · `/metrics` (Prometheus) · `/metrics/summary` (p50/p95/p99 مقابل هدف الثلاث ثوانٍ).

## قرارات تقنية تحتاج اعتماد iValue

مطبّقة الآن بافتراضات صريحة وقابلة للعكس بتغيير تهيئة، لا بتغيير كود:

1. **معادلة الاحتساب.** الـ BRD (ص 7) يقسم على *عدد الأسئلة*، وهذا يُخرج النتيجة عن مقياس ١–٥ متى اختلفت الأوزان (ثلاث إجابات بدرجة ٥ ووزن ٢ تعطي ١٠). المطبّق هو المتوسط المرجّح `Σ(الدرجة × الوزن) ÷ Σ(الأوزان)`. صيغة الـ BRD الحرفية متاحة بتغيير `formula` إلى `brd_literal` في `scoring_config`، وتُصدر تحذيراً. الاختبار الذي يوثّق الفرق: `backend/tests/test_scoring.py::test_weighted_average_stays_within_scale`.
2. **«غير منطبق».** مستبعد من البسط والمقام (محايد). البديل `na_handling: "zero"` جاهز.
3. **تسميات مستويات النضج.** اعتُمدت تسمية جدول الـ BRD ص 6 (تأسيسي / ناشئ / مُعرَّف / مُدار / متميّز) لا تسمية ص 8 المتعارضة معها.
4. **حد أدنى للتغطية.** محور أُجيب على أقل من ٦٠٪ من أسئلته لا يُحتسب في النتيجة الكلية، ويظهر السبب في النتائج. القيمة قابلة للتهيئة.
5. **عدد المستندات لكل سؤال.** بُنيت العلاقة متعدد-إلى-متعدد (FR-16) لا واحد-لواحد (FR-14)، لأن تغييرها لاحقاً يمسّ الاحتساب وتقارير الأدلة.

## المحتوى مؤقّت

`backend/app/db/seed_data/remas_v1.json` يحتوي على **١٦ محوراً و٨٠ سؤالاً** كُتبت لتغطية سلسلة قيمة المطوّر العقاري وتشغيل المحرك من طرف إلى طرف. **هذا محتوى مبدئي يُستبدل بالكامل** بملف المحتوى الرئيسي المعتمد من iValue (١٦ محوراً و١٦٠ سؤالاً بالأوزان ومعايير النضج ومصفوفة الأدلة). المحتوى بيانات لا كود، فاستبداله لا يمسّ أي سطر من المنطق.

```ts
  "brand-700": "#1e3a5c",   // ← غيّر هذا السطر
  "accent-500": "#b8863b",
  "m-1": "#c9d2db",          // سلّم النضج ١←٥
  ...
};
export const dark = { ... };   // الوضع الليلي، بنفس الأسماء
```

غيّر قيمة واحدة هنا فتتغيّر في **كل شاشة**: الأزرار، البطاقات، الشرائح، الجداول،
مقياس ١–٥ في الاستبيان، أشرطة المحاور، الخريطة الحرارية، الرادار، وشعار المنصة.

كيف يعمل ذلك:

1. `palette.ts` يصدّر `paletteCss()` التي تحوّل الكائن إلى متغيّرات CSS.
2. `ThemeStyle` يحقنها في `<head>` من الخادم، فتصل في **أول بايت من الصفحة** — لا وميض ولا فجوة hydration.
3. كل ملف آخر — `globals.css` وكل مكوّن — يقرأ عبر `var(--token)` فقط.

للتحقق من أن القاعدة محفوظة:

```bash
cd frontend
grep -rInE '#[0-9a-fA-F]{3,8}|rgba?\(' src --include='*.tsx' --include='*.css'   | grep -v 'src/theme/palette.ts' | grep -v color-mix
# لا نتائج = لا لون واحد مكتوب خارج ملف الـ palette
```

الملف يحوي أيضاً الرموز غير اللونية (المسافات، أنصاف الأقطار، سلّم الخطوط)، فالنظام كله في مكان واحد.

**أوضاع العرض الثلاثة** مدعومة: تلقائي (يتبع النظام) · ليلي · نهاري، بزر بجانب زر اللغة. الاختيار محفوظ ويُطبَّق قبل أول رسم للصفحة.

### كيف تعمل ثنائية اللغة

المحتوى ليس مترجماً في الواجهة — كل صف في قاعدة البيانات يحمل `_ar` و`_en`، وكل استجابة API تعيد الاثنين معاً. زر اللغة يغيّر أي حقل يُعرض فقط، فلا طلب شبكة ولا إعادة تحميل ولا فقد للإجابات المكتوبة. رسائل الأخطاء من الباك إند تعود هي الأخرى بالحقلين `message_ar` و`message_en` للسبب نفسه. التخطيط كله بخصائص CSS المنطقية (`margin-inline-start` لا `margin-left`)، فالانعكاس بين RTL وLTR يحدث بلا ورقة أنماط ثانية.
